sistema ELC - LEDA, melhorar os RNFs, produtizá-lo e por fim, adicionar

novas funcionalidades da linha de produto, como por exemplo, a geração de casos de teste automática partindo de modelos e, a disponibilização de serviços para utilização de ferramentas online.

\subsection{Riscos Arquiteturais Críticos}

As decisões de projeto para o sistema ELC seguem um padrão de projetos amplamente utilizado pela comunidade, o qual reúne FLEX, JAVA e MYSQL. Essa combinação tem gerado bons frutos em diversos setores da engenharia de software, tais como produtividade, inovação, segurança, entre outros. No entanto, alguns riscos são de conhecimento geral.
 
A interface com o usuário, Flex + Action Script, apresenta dois riscos críticos, que podem ser contornados com a utilização de técnicas básicas.
 
O primeiro deles é a incompatibilidade entre os objetos em ActionScript com objetos Java. Caso não sejam tomadas às devidas precauções, a comunicação entre os dois pode gerar objetos ou atributos de objetos nulos, sem motivo e especificação prévia, o que compromete a confiabilidade do sistema. Uma solução para esse problema é o mapeamento de dados entre as duas linguagens, o que pode ser feito de duas formas: criação de BEANS (objetos semelhantes aos objetos Java, para realizar conversão de tipos) ou utilizar o padrão Command (Framework Cairngorm) que quebra os objetos em seus atributos e passa-os como parâmetros.
 
O segundo risco crítico está relacionado com a dependência do Adobe Flash Player para a exibição da interface gráfica. Constatou-se que plugins antigos do flash player exibem interfaces incompletas e com falhas na execução, como é o caso das versões mais antigas para o sistema operacional Linux que não possuem mapeamentos de caracteres com acentuação, ou seja, caracteres acentuados nestas versões se transformam em caracteres indesejados. Para o correto funcionamento deste, é preciso manter o plugin atualizado nos terminais clientes.

A utilização de Servlets como provedores de serviços cria um risco adicional. Estes serviços utilizados para enviar e-mails, fazer download e upload de arquivos, utilizam os métodos doPost e doGet que podem ser acessados facilmente por atacantes, comprometendo assim a segurança do sistema. Para contornar esse problema, necessita-se unir a execução destes métodos a uma sessão do usuário, para que só sejam executados por usuários credenciados.

Outro risco crítico está na política de Backup do banco de dados. O administrador responsável pelo sistema deve sempre verificar se o backup dos dados está realmente sendo enviado para o local correto.

Por fim, o risco de estouro de memória ao realizar vários deployments no servidor Tomcat. É de amplo conhecimento da comunidade que o Tomcat não tem uma boa política de administração de deployments das aplicações. Com o Flex requer uma grande carga de deployment, por motivos desconhecidos provoca-se estouro de memória e ocasiona travamento temporário das aplicações hospedadas. Para contornar esse risco, por hora, deve-se evitar usar o Tomcat Manager e utilizar o deployment manual na pasta de aplicações.

\section{Visão Lógica}

\subsection{Questionário para escolha do Padrão Arquitetural}
\label{quest}

Após analisar as condições do sistema implantado atualmente, as possíveis
funcionalidades adicionais e os Requisitos Funcionais e Não-Funcionais do novo
Sistema, foram respondidas algumas questões fundamentais para o projeto da
arquitetura, baseadas em [SOMMERVILLE 2010].

\begin{itemize}
  \item Existe uma arquitetura de aplicações genérica que pode agir como
  template para o sistema que está sendo projetado? \newline
  \textit{Sim, o template de Transaction-Processing Systems, mais
  especificamente, de Sistemas de Informação. Esse tipo de sistema é
  caracterizado por permitir acesso controlado a uma grande base de informação,
  um banco de dados compartilhado por exemplo. O mesmo é modelado usando o
  padrão arquitetural de camadas (ou máquina abstrata, ver Figura \ref{fig2}).}
  \begin{figure}[h]
		\centering
		\includegraphics[scale=0.5]{imagens/camadas.png}
		\caption{Modelo de Camadas ou Máquina Abstrata}
		\label{fig2}
	\end{figure}
	\item Como o sistema será distribuído através de processos? \newline
	\textit{O ELC será distribuído entre os vários clientes e um servidor}
	\item Qual ou quais estilos arquiteturais são apropriados para o sistema?
	\newline
	\textit{O modelo de camadas unido com o cliente-servidor (ver Figura
	\ref{fig3}). O primeiro é responsável por organizar o acesso à base de dados.
	As múltiplas camadas modularizam o sistema, garantem portabilidade entre vários ambientes, por dividir deveres em vários níveis, e.g a camada inferior é a única a comunicar-se com o hardware. E, principalmente, flexibiliza a arquitetura horizontalmente, pois facilita o acréscimo de funcionalidades localizadamente na arquitetura, sem preocupar-se com os níveis inferiores. O último permite que separemos o sistema em 3 níveis básicos: os clientes remotos, pela web; o servidor de processamento de aplicações, com os serviços e funcionalidades do sistema e; o servidor de administração de dados, o servidor de Banco de Dados. O ELC é uma linha de produto que oferece ambientes web de apoio ao ensino de programação. Portanto, a opção de arquitetura híbrida proposta permite ter a flexibilidade requisitada por uma linha de produto, a manipulação dos estados de um ambiente de programação e a disponibilidade da web.} \begin{figure}[h]
		\centering
		\includegraphics[scale=0.5]{imagens/arquitetura.png}
		\caption{Arquitetura Cliente-Servidor de três camadas}
		\label{fig3}
	\end{figure}
	\item Qual será a abordagem fundamental usada para Estrutura o sistema?
	\newline \textit{O modelo de camadas formará a base	principal do sistema, no
	entanto, este terá alguns componentes adicionais da arquitetura cliente-servidor.}
	\item Como as estruturas unitárias do sistema são decompostas em módulos?
	\newline \textit{Iremos utilizar uma decomposição orientada a objetos, com
	uma modularização através de componentes.}
	\item Qual estratégia será utilizada para controlar as operações das unidades
	do sistema? \newline \textit{Duas estratégias serão utilizadas. A primeira será
	o controle centralizado com o modelo de call-return, que executará as requisições às camadas de comunicação, processamento e dados sequencialmente. E a segunda estratégia é o Broadcast model, utilizada para sistemas orientados a eventos, no caso, a GUI comunica-se com o restante do sistema através de eventos e as requisições de serviço ao servidor (modelo cliente-servidor) podem também ser considerados eventos.}
	\item Alguma desvantagem pode ser prevista nesse modelo? \newline \textit{Sim,
	as mudanças em camadas inferiores são custosas, as camadas diminuem também a eficiência e ao trabalhar com uma arquitetura híbrida o projeto do sistema e a criação de novos componentes deve ser cuidadosa para escolher a melhor forma de implementação.}
	\item Como a arquitetura será avaliada? \newline \textit{Pelo cliente
	inicialmente, em sala de aula através da avaliação de pares e pela professora, ao término.}
\end{itemize}

\subsection{Estrutura da Arquitetura Linha de Produto ELC}
\label{estrutura}

\subsubsection{Arquitetura Geral da Linha de Produto - ELC}

Na seção \ref{quest} foram expostas as vantagens para seleção dessas
arquiteturas. Aqui são apresentados alguns comentários adicionais e a representação através de diagramas de componentes.

\begin{figure} [h]
	\centering
		\includegraphics[scale=0.35]{imagens/estruturaArquitetura.png}
	\caption{Diagrama de Componentes Completo da Linha de Produto ELC}
	\label{diagramaComponentes}
\end{figure}

O diagrama (Figura \ref{diagramaComponentes}) está dividido em 3 pacotes, os quais
representam as três camadas da arquitetura \textit{Three Tier Client-Server
Model}.

O \textit{Remote Client} representa um \textbf{cliente gordo}, Web browser +
SWFs (Flex + ActionScript + JavaScript). Ao optar por Flex, considera-se que todas as páginas acessadas serão carregadas para o computador do usuário e juntamente com os arquivos de descrição da interface (.mxml), são carregados também arquivos ActionScript, de processamento da interação com o usuário. Além dos arquivos de configuração do browser em JavaScript.
 
O \textit{Application Processing Server - Tomcat Server} é formado por Servlets
que recebem requisições, processam os dados e respondem para o cliente. Os quais são usados para os serviços de upload, download, envio de email, execução de ferramentas. Portanto, os mesmos são utilizados basicamente para oferecer serviços que não guardam estados, ou seja, não acessam o banco de dados.

O \textit{Data Manager Server} está na terceira camada que se divide em Banco de
Dados MySQL e rotinas de leitura e escrita no servidor.

A característica marcante de ser um sistema de informação permite dividir parte
do diagrama em camadas menores internas seguindo o \textit{Layered Model}. 
Assim, a camada inicial é composta pelo servidor de banco de dados MySQL, a qual
comunica-se através do hibernate (regras de mapeamento) com a camada superior. A
segunda camada, recuperação e modificação da informação é composta pela lógica
de negócios (dividida entre os \textit{Managers}) que comunica-se com a camada
superior através do sistema e de sua fachada (\textit{System} e
\textit{Facade}).  A terceira camada, comunicação com os usuários, manipula os formulários preenchidos pelo usuários. E por último, o browser através do plugin flash player e os SWFs do sistemas provêem as telas do sistema para o usuário final.

\subsubsection{Exemplo de Autenticação de Usuário}

Com o objetivo de melhorar o entendimento do diagrama de componentes, essa seção
explica o fluxo de execução e a troca de mensagens durante a autenticação de um usuário.

\textbf{Camada de Apresentação e Cliente Remoto}

O Web Browser com o plugin \textit{Adobe Flash Player} instalado compõem o
ambiente de execução do sistema ELC no cliente remoto. Ao enviar a requisição de
acesso à página de autenticação do sistema, o browser executa o plugin,
conecta-se com o servidor e carrega os módulos SWF necessários para execução do
sistema. Um \textit{SWF} (também conhecido como um módulo de visão) é formado
por mapeamentos de eventos dos componentes Flex com seus respectivos códigos
Action Script e com a \textit{Facade} do sistema. O \textit{Action Script}
utiliza outros módulos auxiliares para lançamento e captura de eventos, por exemplo (\textit{Action
Script Event}), como também requisita URLs para um módulo em JavaScript caso
necessite utilizar um serviço em particular do ELC (\textit{e.g.} download).

\begin{figure} [h]
	\centering
		\includegraphics[scale=0.5]{imagens/interface.png}
	\caption{Diagrama da Interface com o Usuário}
	\label{interface}
\end{figure}

\textbf{Camada de Lógica de Negócios e Serviços }

Após carregar a página inicial do sistema, o usuário digita seu \textit{login} e
senha e clica em entrar. Com essa ação lança-se um evento para GUI, que é
devidamente tratado e uma requisição HTTPS é enviada para o servidor de
aplicações. No caso de autenticação, é realizada uma chamada à \textit{ELC Logic
Facade} (reúne toda a API de manipulação e recuperação de dados do ELC) que
repassa para o \textit{System} (componente responsável pela lógica do sistema) e
este realiza delega as atividades aos \textit{Managers}. O \textit{System} é um
componente agregador e manipulador de dados, pois apenas realiza chamadas aos
\textit{Managers}. Estes últimos são os reais conhecedores das regras de
negócio, são criados de acordo com os requisitos funcionais do sistema, possuem
atribuições bem definidas e são independentes entre si. Cada \textit{Managers}
manipula objetos \textit{POJO} através de seus métodos públicos (POJO Methods) e
pode também realizar chamadas à \textit{DB Transaction API}.

\begin{figure} [h]
	\centering
		\includegraphics[scale=0.5]{imagens/logicaNegocios.png}
	\caption{Diagrama da Lógica de Negócios e Serviços}
	\label{logicaNegocios}
\end{figure}

Uma segunda forma de acessar o \textit{Application Processing Server} é através
de \textit{Servlet URLs}. O servidor possui um \textit{Servlet Container} com alguns serviços como download ou upload de arquivos, envio de email, entre outros. Estes serviços são providos através de métodos \textit{doPost} apenas (Flex estabelece essa restrição para melhorar a segurança do sistema), sua implementação utiliza-se da \textit{Services Facade}. Essa \textit{Facade} trata de processar os serviços, e retornar os valores, mais precisamente o EmailManager que reutiliza um determinado \textit{SMTP Service} externo e o \textit{FileManager} lida com a leitura e escrita de arquivos no Servidor de dados.

\textbf{Camada de Banco de Dados e Manipulação de Arquivos}

Continuando a requisição de autenticação pelo usuário, a transação de consulta do banco de dados é implementada pelo componente \textit{DAO Hibernate}, que através do padrão DAO evita a replicação de código nas transações. Ao chamar um método de um objeto do padrão DAO, uma string é traduzida em transação através do \textit{Hibernate Framework}, onde é feita a comunicação direta com o \textit{MySQL Database}.

Ao retornar a senha do usuário que deseja autenticar-se, cria-se o objeto devido com os atributos simples retornados pela consulta e esse objeto é retornado sequencialmente via todas as chamadas anteriores até ser comparado com a senha digitada.
