\section{Motivação e Objetivo do Sistema}

\subsection{Contexto}

Desde meados da década de 1960, o estudo de linguagens de programação é o primeiro alvo dos cursos de Ciência da Computação por todo o mundo, e naquela época já se pensava em como utilizar o próprio computador para avaliar os programas dos alunos. Muitas linhas de pesquisa foram desenvolvidas utilizando-se desse argumento: como avaliar o produto da criação de seres humanos?

Muitos anos passaram, novas descobertas, tecnologias e soluções foram desenvolvidas, no entanto, novos problemas surgiram, o número de estudantes aumentou, a quantidade de paradigmas e linguagens de programação criam polêmicas para a tarefa de escolher a mais apropriada para o ensino, a internet facilita a cópia de soluções prontas, o aumento da quantidade de tarefas dedicadas aos tutores e a delegação de atividades de correção aos assistentes (monitores) diminuiu a confiabilidade e aumentou os critérios de correção das atividades. Então, como avaliar atividades de programação atualmente, mantendo um padrão da correção e garantindo um bom nível de confiabilidade?

Esse problema foi identificado no Curso de Ciência de Computação da Universidade
Federal de Campina Grande. A solução proposta é a criação de um ambiente de
suporte a atividades de programação. O sistema \textit{Easy Lab Correction} (ELC) tem como meta reunir as necessidades dos tutores, assistentes e alunos em um ambiente online de criação, correção das atividades, suporte (com ferramentas online) e submissão de soluções, discussão das notas e outras funcionalidades que propiciarão maior agilidade, padronização e segurança nas atividades de laboratório de programação.

\subsection{Atualmente \ldots}

O ELC encontra-se em uso na disciplina de Laboratório de Estrutura de Dados (LEDA) com o professor Adalberto Cajueiro (cliente do projeto). Esse estado de implantação constante do sistema (beta) juntamente com uma revisão bibliográfica sobre a automatização de correções de exercícios de programação permitiu a visualização de uma linha de produto de software nesse nicho. Para tanto um novo estudo arquitetural do sistema é necessário, dado que a versão atual não foi concebida com características de reusabilidade.

\subsection{Estudo do conceito de Linha de Produto}

Uma Linha de Produto de Software consiste em um conjunto de aplicações com uma arquitetura comum. Cada aplicação é especializada a partir de um subconjunto de funcionalidades centrais e genéricas comum.
 
Vários são os tipos de especialização que a família de aplicações pode ser
desenvolvida [Sommervile 2010], a linha de produto ELC (beta) segue a
\textit{especialização funcional}, na qual versões de aplicações são criadas para clientes específicos com requisitos diferentes. Assim, apenas os componentes das funcionalidades do sistema devem adaptar-se ou novas funcionalidades devem ser adicionadas. Questões como mudança de plataforma ou de ambientes não são considerados.

Linhas de Produto de Software são projetadas para serem reconfiguradas, ou seja, devem ser genéricas e permitir facilmente sua especialização. Essa reconfiguração pode acontecer em dois momentos, no momento da implantação ou no momento de projeto do novo membro da família de aplicações. O primeiro caso é amplamente utilizado em pacotes de software verticais projetados para aplicações específicas e com alto grau de similaridade, nesses casos a arquitetura deve ser amplamente reconfigurável não necessitando de acréscimos de funcionalidades no momento de implantação do software, o que requer ampla experiência da equipe de elicitação de requisitos e de desenvolvedores no nicho escolhido. A segunda forma de reuso ocorre em tempo de projeto, e partes do código fonte do núcleo do sistema pode ser modificado o que permite uma maior flexibilidade.

Para o projeto ELC foi escolhida a segunda alternativa devido a pouca experiência da equipe e, principalmente, o baixo número de funcionalidades atualmente desenvolvidas. Dessa forma, a equipe de desenvolvimento discutirá uma nova arquitetura que englobe não apenas as necessidades de um cliente, mas permita que uma série de requisitos funcionais e não funcionais sejam desenvolvidos ou adaptados.
 
Para adaptar uma linha de produto em uma única aplicação alguns passos são necessários:

1.	Elicitar os requisites dos stakeholders;

2.	Escolher o membro da família com maior similaridade;

3.	Renegociar os requisitos;

4.	Adaptar o sistema existente;

5.	Entregar o novo membro da família ao cliente.

\subsection{Objetivo do Projeto}

Portanto, o projeto \textit{Easy Lab Correction} na disciplina de Projeto I tem
dois objetivos básicos: desenvolver uma arquitetura de linha de produto de software
robusta com as características acima citadas e instanciar uma primeira aplicação
para o cliente Adalberto na disciplina LEDA. Como trabalhos futuros (na
disciplina de Projeto II) propõe-se buscar novos clientes com necessidades
similares e assim
expandir a família de aplicações.

\section{Stakeholders}

Os \textit{stakeholders} envolvidos no Sistema são:
\begin{itemize}
  \item Cliente e Professor: Adalberto Cajueiro, professor da disciplina de
  Laboratório de Estrutura de Dados;
  \item Monitores: alunos veteranos do curso selecionados para dar suporte à
  disciplina;
  \item Alunos: alunos da disciplina LEDA;
  \item Desenvolvedores, Testadores, Gerente de Projeto e Arquitetos: equipe
  de desenvolvimento do sistema, responsável por elicitar requisitos, planejar,
  desenvolver, acompanhar, testar e implantar o sistema.
\end{itemize}
